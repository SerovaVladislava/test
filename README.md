# AI-помощник для подготовки карточек товаров КИП

Прототип сервиса, который по данным о контрольно-измерительном приборе готовит черновик карточки товара
для B2B-интернет-магазина:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- структурированный список ключевых характеристик с источником каждого значения;
- 3–5 поисковых запросов;
- commercial-блок для менеджера: кому подходит прибор и какие задачи решает;
- список того, чего не хватает во входных данных или что требует уточнения.

Технические значения берутся **только из входных данных**. Если характеристики нет, в карточке стоит
«данных нет», а поле попадает в список «Чего не хватает в данных». Каждый ответ модели проходит
автоматическую проверку: длина текстов, полнота характеристик и отсутствие чисел, которых нет на входе.

LLM на выбор, все со строгой JSON-схемой ответа и одной и той же автопроверкой:

| Провайдер | Модель по умолчанию | Стоимость | Когда выбирать |
|---|---|---|---|
| **Claude** (Anthropic API, официальный SDK) | `claude-opus-5-5` | платный ключ | лучшее качество |
| **OpenRouter** (любой OpenAI-совместимый API) | `nvidia/nemotron-3.5-super-vl:free` | бесплатный ключ, без карты | бесплатно и без нагрузки на компьютер |
| **Ollama** (локально) | `qwen2.5:7b` | бесплатно, без ключа | данные не покидают компьютер; нужна память и время |

## Быстрый старт

Нужен Python 3.10+ и один из провайдеров из таблицы выше.

```bash
git clone <URL репозитория> && cd <папка репозитория>
python -m venv .venv
```

Активируйте окружение: в Windows (PowerShell) — `.venv\Scripts\Activate.ps1`, в Linux/macOS — `source .venv/bin/activate`. Затем:

```bash
pip install -r requirements.txt
cp .env.example .env        # в Windows: copy .env.example .env
```

Дальше настройте один из провайдеров в `.env` (файл указан в `.gitignore`, ключа в коде нет):

- **Claude:** впишите ключ в строку `ANTHROPIC_API_KEY=`.
- **OpenRouter (бесплатно):** зарегистрируйтесь на [openrouter.ai](https://openrouter.ai) (почта или
  Google, карта не нужна), создайте ключ на странице [Keys](https://openrouter.ai/keys), поставьте
  `CARD_PROVIDER=openrouter` и `OPENROUTER_API_KEY=sk-or-…`. У бесплатных моделей есть лимит запросов
  в минуту и в день; при ответе 429 сервис сам повторяет запрос через 10 и 30 секунд.
- **Ollama (локально):** поставьте `CARD_PROVIDER=ollama` и скачайте модель (~4,7 ГБ):

  ```bash
  ollama pull qwen2.5:7b
  ```

  Модели нужно ~6 ГБ **свободной** оперативной памяти; видеокарта не обязательна, но без неё карточка
  пишется несколько минут. При нехватке памяти Windows уходит в подкачку и может перестать отвечать —
  проверено на компьютере с 8 ГБ. Модель `qwen2.5:3b` занимает ~2,5 ГБ, но пишет заметно хуже (см. «Примеры»).

Сгенерировать карточку из JSON:

```bash
python -m card_generator generate examples/input/03_dm02_task_example.json -o output
```

Результат появится в `output/` в двух видах: `*.json` (для интеграции) и `*.md` (для вычитки и копирования).

Веб-форма:

```bash
python -m card_generator serve
```

Затем откройте http://127.0.0.1:5000. Данные можно ввести полями формы или вставить JSON.
На странице результата у каждого блока есть кнопка «Копировать».

Тесты (работают без ключа и без сети, модель подменяется заглушкой):

```bash
python -m pytest
```

## Команды

| Команда | Что делает |
|---|---|
| `generate INPUT.json [-o DIR] [--name STEM]` | Генерирует карточки. INPUT — один товар (объект) или несколько (массив) |
| `check INPUT.json` | Проверяет входной JSON без обращения к LLM: ошибки и пробелы в данных |
| `from-feed FEED.xml --offer-id ID [--offer-id ID2] [-o OUT.json]` | Выгружает товары из YML-фида во входной JSON |
| `search-feed FEED.xml "запрос"` | Ищет офферы в фиде по названию, типу или производителю |
| `serve [--port 5000]` | Запускает веб-форму и JSON API |

Все команды запускаются как `python -m card_generator <команда>`; флаг `-v` включает подробный лог.

HTTP API (поднимается командой `serve`):

```bash
curl -X POST http://127.0.0.1:5000/api/generate -H "Content-Type: application/json" --data-binary @examples/input/03_dm02_task_example.json
```

- `POST /api/generate` — JSON товара → JSON результата; `400` — ошибка во входных данных, `502` — ошибка LLM,
  `503` — не задан ключ Anthropic;
- `POST /api/check` — только проверка входа, без LLM.

## Входные данные

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {"диапазон измерений": "0–1,6 МПа", "класс точности": "1,5"},
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

- `name` — обязательно. Без него генерация не запускается.
- `manufacturer`, `specs`, `description` — желательно. Если поля нет, генерация всё равно идёт, но поле
  попадает в пробелы данных, а модель получает об этом явное указание.
- `specs` принимается в виде объекта `{"название": "значение"}`, вложенных объектов
  (`{"питание": {"напряжение": "24 В"}}` → «питание / напряжение») или списка `[{"name": …, "value": …}]`.
  Пустые значения (`""`, `"-"`, `"н/д"`, `null`) не считаются характеристикой и попадают в пробелы данных.
- HTML в описании очищается, числа приводятся к строкам.
- Прочие поля (`category`, `sku` и т. п.) передаются модели как дополнительные данные. Служебные
  (`url`, `feed_offer_id`, `price`) сохраняются в результате, но модели не передаются.

Некорректный JSON, пустой `name`, неверные типы полей дают понятное сообщение с указанием места ошибки,
например: `Некорректный JSON: пропущена запятая между элементами (строка 6, столбец 3)`.

## Результат

JSON (`CardResult`):

```text
status        ok | needs_review — пройдены ли все автопроверки
product       нормализованные входные данные
card
  seo_title, seo_description
  key_specs[]     {name, value, source}; source: характеристики | описание | название товара | данных нет
  search_queries[]
  commercial      {audience[], tasks[], pitch}
  data_gaps[]     {field, status: отсутствует | требует уточнения, comment}
issues[]      замечания автопроверки, оставшиеся после всех попыток
autofixes[]   что код исправил в ответе модели сам (например, вернул потерянную входную характеристику)
stats         длины текстов, число характеристик и пробелов
meta          модель, число попыток, токены, сработал ли fallback
```

Markdown-версия содержит те же блоки в порядке, удобном контент-менеджеру, с таблицей характеристик и
таблицей «Чего не хватает в данных».

### Результаты

Примеры сгенерированы бесплатной моделью `nvidia/nemotron-3.5-super-vl:free` через OpenRouter
(`CARD_PROVIDER=openrouter`). Ключа Claude при подготовке задания не было; код для Claude тот же, меняется
только провайдер.

| Пример | Статус | Попыток | Заголовок, симв. | Описание, симв. | Характеристик (из них «данных нет») | Время |
|---|---|---|---|---|---|---|
| 1. МП4-У | ok | 2 | 60 | 1017 | 10 (6) | 83 с |
| 2. ПД100И | ok | 3 | 68 | 1169 | 10 (7) | 276 с |
| 3. DM 02 | ok | 1 | 54 | 945 | 12 (5) | 89 с |

Что видно по карточкам:

- **МП4-У** (только название из фида): диапазон «0...60 кгс/см²» и класс точности «кл.т 1,5» взяты из
  названия с источником «название товара», без перевода кгс/см² в МПа. Остальное — «данных нет»
  с конкретными запросами: резьба и расположение штуцера, диаметр корпуса, IP, климатическое исполнение.
- **ПД100И** (только название): код модификации не расшифрован, взрывозащищённость упомянута только
  как факт из названия, маркировка взрывозащиты — «требует уточнения». Первая попытка оборвалась:
  модель с рассуждениями исчерпала лимит ответа в 16 тыс. токенов. Сервис повторил запрос; во второй
  попытке автопроверка нашла 9 замечаний, третья прошла чисто.
- **DM 02** (полные данные): все 4 входные характеристики дословно; модель заметила, что описание
  во входе обрывается на «...», и вынесла это в пробелы данных.
- При вычитке ещё стоит поправить шероховатые SEO-вставки («датчик давления промышленный купить можно…»)
  и общие фразы в третьем абзаце. Это работа редактора: автопроверка проверяет факты, а не стиль.

### Сравнение: локальная модель qwen2.5:3b

Те же входы на `qwen2.5:3b` через Ollama (процессор без видеокарты, 8 ГБ ОЗУ, ~5,5 мин на карточку)
дали `needs_review` у всех трёх:

- описание 258–341 символ при норме 800–1200 даже после трёх попыток с замечаниями;
- из 4 входных характеристик DM 02 потеряны 2 — теперь их возвращает код (`autofixes`);
- выдумано «питается от сети 220 Вт» — поймано проверкой чисел;
- иероглифы в названии характеристики и «класс точности 1,0», взятый из кода «ДИ1,0». Эти ошибки исходные
  проверки пропускали; проверки `foreign_script` и `code_value` добавлены по итогам этого прогона.

Вывод: автопроверка не даёт слабой карточке пройти со статусом `ok`, но качество текста определяется
моделью, и 3B для такой задачи мало. Модель `qwen2.5:7b` на компьютере с 8 ГБ не запустилась: при
загрузке не хватило памяти и система перестала отвечать.

## Как это устроено

```text
JSON / форма / фид
      │
      ▼
input_validation ── ошибка? → понятное сообщение, LLM не вызывается
      │  пробелы в данных (нет описания, пустые характеристики…)
      ▼
prompts ── системный промпт (неизменный, кэшируется) + <product_data> + <input_check>
      │
      ▼
llm ── Claude / OpenRouter / Ollama, строгая JSON-схема ответа
      │
      ▼
postcheck ── потерянные входные характеристики возвращает сам;
      │      проверяет длины, количество запросов, числа не из входных данных, Markdown, «лучший»
      │  есть замечания? → повтор: черновик + список замечаний (до CARD_MAX_ATTEMPTS попыток)
      ▼
CardResult → JSON + Markdown
```

| Модуль | Назначение |
|---|---|
| `card_generator/input_validation.py` | Разбор JSON, нормализация, ошибки и пробелы в данных |
| `card_generator/prompts.py` | Системный промпт и сборка пользовательского сообщения |
| `card_generator/llm.py` | Провайдеры Claude, OpenRouter и Ollama, разбор ответа, перевод ошибок в понятные сообщения |
| `card_generator/config.py` | Настройки из `.env` и окружения с проверкой значений |
| `card_generator/postcheck.py` | Детерминированная проверка ответа модели |
| `card_generator/service.py` | Оркестрация и цикл повторов с замечаниями |
| `card_generator/render.py` | Markdown-представление |
| `card_generator/feed.py` | Импорт из YML-фида |
| `card_generator/cli.py`, `web.py` | CLI, веб-форма (Flask) и JSON API |

## Промпт и принятые решения

**Структура промпта** ([prompts.py](card_generator/prompts.py)). Системный промпт задаёт роль (копирайтер
B2B-магазина КИПиА), аудиторию и восемь правил работы с фактами, затем требования к каждому полю.
Данные товара передаются в теге `<product_data>`. Модели прямо сказано, что это данные, а не инструкции:
это защита от промпт-инъекций в описаниях. Результаты проверки входа идут отдельным блоком
`<input_check>`, поэтому модель знает, чего не хватает, и не пытается это «восполнить».

**Правила против выдумывания** — главная часть промпта:

- значения переписываются дословно, без перевода единиц (кгс/см² не превращается в МПа) и округления;
- коды модификаций (`-111-`, `ДИ1,0`, `М23`) не расшифровываются, если расшифровки нет во входе:
  модель просит подтвердить их по паспорту;
- из названия берутся только параметры, записанные явно с единицами («0...60 кгс/см²», «кл.т 1,5»);
- общие знания о типе прибора допускаются только качественно и без чисел («манометры применяются в
  системах отопления…»). Пригодность для особых условий (взрывоопасные зоны, агрессивные среды,
  коммерческий учёт) заявлять нельзя, если её нет в данных: это технические утверждения в обёртке маркетинга;
- противоречия и неоднозначности модель не разрешает сама, а выносит в «требует уточнения».

**Длина описания через структуру.** Модели плохо считают символы, зато хорошо держат структуру.
Поэтому описание задано как ровно 3 абзаца по 3–4 предложения с заданным содержанием (назначение;
характеристики и что они дают; применение), плюс ориентир в словах (120–160). Модели 3B это не помогло:
и с этой структурой, и без неё она писала 260–340 символов, — нижняя граница качества, ниже которой
автопроверка уже не спасает (см. «Примеры»).

**Структурированный вывод.** Ответ строго соответствует JSON-схеме, построенной из Pydantic-модели
([models.py](card_generator/models.py)): API гарантирует валидный JSON нужной формы. Порядок полей в схеме
выбран намеренно: сначала `key_specs` и `data_gaps`, затем `search_queries`, и только потом тексты.
Модель генерирует JSON по порядку, поэтому к написанию описания у неё уже зафиксированы факты и запросы,
которые нужно органично вписать в текст.

**Автопроверка и повтор** ([postcheck.py](card_generator/postcheck.py)). Модели плохо считают символы
и иногда пересказывают значения, поэтому всё проверяемое проверяется кодом:

- длина заголовка и описания, количество запросов, заполненность блоков;
- **каждое число** в заголовке, описании, запросах, commercial-блоке и характеристиках должно
  встречаться во входных данных. Учитываются разные записи одного числа: `1,6` = `1.6`, `1 000` = `1000`,
  `02` = `2`. Числа из URL и id оффера не считаются разрешёнными;
- каждая входная характеристика должна попасть в `key_specs` с неизменённым значением. Если модель
  её потеряла или пересказала, код сам возвращает входное значение — это известный факт, переспрашивать
  модель незачем. Такие правки перечислены в результате (`autofixes`, раздел «Исправлено автоматически»);
- в текстах нет Markdown-разметки и рекламных оценок: «лучший», «№1», «идеально подходит», «высокая точность»;
- **числа из кода модификации** не используются как параметры. Если число встречается во входных данных
  только внутри кода (`1,0` в «ПД100И-ДИ1,0-111-0,5-ЕХI»), его можно упоминать лишь в составе модели:
  «класс точности 1,0» — это уже расшифровка кода, которой во входе нет. Обычная проверка чисел такое
  пропускает, ведь число во входе есть;
- нет символов чужой письменности (иероглифов и т. п.) — небольшие модели иногда вставляют их в русский текст.

При замечаниях модель получает свой черновик и конкретный список проблем («SEO-описание 1342 символа,
сократите минимум на 142»), всего до 3 попыток (`CARD_MAX_ATTEMPTS`). Если замечания остались, возвращается
лучшая попытка со статусом `needs_review` и списком замечаний: ничего не обрезается молча.

**Модель и параметры.** `claude-opus-5-5` с `effort: medium` — баланс качества русского текста и стоимости;
меняется через `.env`. Включены:

- кэширование системного промпта: повторные попытки и пакетная генерация дешевле;
- серверный fallback (`fallbacks: "default"`): если классификатор безопасности ошибочно отклонит запрос,
  API сам повторит его на рекомендованной модели. Отключается `CARD_FALLBACKS=off`; при смене модели на
  ту, что не поддерживает fallback, его тоже нужно отключить.

**Локальная модель (Ollama).** Тот же промпт, та же схема и та же автопроверка — меняется только
провайдер (`CARD_PROVIDER=ollama`), поэтому качество двух моделей можно сравнивать на одних и тех же
проверках. Особенности:

- схема передаётся в параметре `format`: Ollama ограничивает генерацию грамматикой, и структура JSON
  с допустимыми значениями (`source`, `status`) соблюдается всегда. Ссылки `$ref` в схеме заранее
  раскрываются: старые версии Ollama их не понимают;
- окно контекста задаётся явно (`CARD_NUM_CTX=8192`). По умолчанию у Ollama 2048 токенов, и длинный
  промпт молча обрезается с начала — модель теряет системные правила;
- `temperature: 0.3` и лимит ответа 4096 токенов: меньше «творчества» с фактами и защита от зацикливания;
- таймаут по умолчанию 30 минут: на процессоре без видеокарты 7B-модель пишет 3–5 токенов в секунду.

**Обработка ошибок.**

| Ситуация | Поведение |
|---|---|
| Некорректный JSON, пустое `name`, неверные типы | Сообщение с местом ошибки, LLM не вызывается (CLI: код 2, API: 400) |
| Нет описания или характеристик, пустые значения | Генерация идёт, поля помечаются «данных нет» и попадают в пробелы данных |
| Нет ключа, неверный ключ, модель не найдена | Понятное сообщение без повторов (API: 503 / 502) |
| 429, 5xx, обрыв соединения | SDK сам повторяет запрос 2 раза, затем сообщение об ошибке |
| Ответ обрезан или не соответствует схеме | Повтор генерации с указанием проблемы |
| Отказ модели (`refusal`) | Fallback на другую модель; если и она отказала — сообщение |
| Ollama не запущена, модель не скачана, не хватает памяти | Сообщение с подсказкой («выполните `ollama pull qwen2.5:7b`»), API: 502 |
| OpenRouter: лимит бесплатной модели (429), сбой провайдера (502/503) | Два повтора с паузой 10 и 30 с, затем сообщение |
| OpenRouter: модель не поддерживает JSON-схему | Сообщение с подсказкой `CARD_JSON_MODE=json_object`: схема уходит в промпт, ответ всё равно валидируется |
| JSON в ответе обёрнут в ```` ```json ```` или окружён пояснениями | Извлекается и проверяется по схеме |

## Ограничения и возможные улучшения

Ограничения:

- **Проверка чисел, но не смысла.** Автопроверка ловит выдуманные числа и единицы, но не выдуманные
  качественные утверждения: «корпус из нержавеющей стали», «для агрессивных сред». От них защищает
  только промпт, поэтому черновик всё равно требует вычитки.
- Числа, записанные словами («два выхода»), не проверяются.
- Длина считается в символах с пробелами. Другие правила подсчёта (без пробелов) потребуют правки констант.
- Данных фида недостаточно для полноценной карточки: при пустых характеристиках описание неизбежно
  общее, а список «данных нет» длинный. Это корректное поведение, но не готовый к публикации текст.
- Генерация синхронная (Claude — 30–90 с на товар, бесплатная модель OpenRouter — 1,5–5 мин,
  локальная модель на CPU — минуты), без очереди; веб-форма обрабатывает один товар за раз.
- **Бесплатные модели OpenRouter нестабильны**: у них дневной лимит запросов, популярные модели бывают
  перегружены (при подготовке примеров Gemma 4 отвечала 429 «rate-limited upstream»), а состав бесплатных
  моделей меняется. Для работы с потоком товаров нужен платный ключ — Claude или платная модель OpenRouter.
- Код модификации распознаётся по дефисам между буквами и цифрами («ПД100И-ДИ1,0-111»). Коды без дефиса
  («ДМ2010Сг») проверка `code_value` не видит.
- Нет хранения результатов, истории правок и авторизации — по условию задачи.

Что можно улучшить:

1. **Обогащение данных**: подтягивать характеристики и описание со страницы товара или из PDF-паспорта
   производителя (Claude читает PDF напрямую) — это главный источник качества для данных из фида.
2. **Справочник обязательных характеристик по категориям** (манометр: диапазон, класс точности, диаметр,
   резьба, расположение штуцера…), чтобы список «данных нет» был детерминированным, а не на усмотрение модели.
3. **Второй проход «проверяющим»**: отдельный дешёвый запрос, который ищет в тексте качественные утверждения
   без опоры на данные.
4. **Пакетная обработка фида** через Message Batches API (в 2 раза дешевле) с возобновлением после сбоя.
5. **Набор эталонных карточек и eval**: метрики доли `needs_review`, числа выдуманных значений, оценки
   контент-менеджеров — чтобы менять промпт и модель по данным, а не на глаз.
6. Учёт правил конкретной CMS и SEO-требований магазина (стоп-слова, шаблоны заголовков по категориям).
